## 1. Мета роботи
Здобути практичні навички створення повнофункціонального користувацького інтерфейсу із системою аутентифікації, керуванням станом, валідацією форм та реалізацією CRUD-операцій для взаємодії з API серверної частини.

## 2. Хід роботи та результати

1. **Система аутентифікації:** Налаштовано клієнтський стан через `Zustand` (файл `authStore.ts`), який зберігає токен доступу в `localStorage`. Створено сторінки `LoginPage` та `RegisterPage`. Налаштовано interceptors в Axios для автоматичного додавання токена до запитів та обробки помилки 401 (вихід із системи).
2. **Захищені маршрути:** Створено компонент `ProtectedRoute`, який обмежує доступ до приватних сторінок неавторизованим користувачам і перенаправляє їх на сторінку входу зі збереженням попереднього маршруту.
3. **Валідація форм:** Використано зв'язку `React Hook Form` та `Zod`. Створено схеми валідації для авторизації та редагування користувачів (`userSchema`). 
4. **Робота з серверними даними:** Встановлено та налаштовано `TanStack Query`. Усі CRUD-операції (отримання списку, створення, редагування, видалення) реалізовано через `useQuery` та `useMutation`.
5. **UI/UX покращення:** 
   - Реалізовано пагінацію та миттєвий пошук із використанням хука `useDebounce` (затримка 300 мс).
   - Додано скелетні індикатори завантаження (`Skeleton`).
   - Налаштовано систему глобальних сповіщень через `react-hot-toast` для інформування про успішні дії та помилки.

## 3. Відповіді на контрольні запитання

1. **Поясніть різницю між контрольованими та неконтрольованими компонентами в React.**
   Контрольовані компоненти керуються станом React (`useState`), і кожне натискання клавіші викликає перемальовування (ре-рендер). Неконтрольовані зберігають стан у DOM і доступні через `ref`. React Hook Form використовує неконтрольований підхід (реєстрація через `ref`), що значно зменшує кількість ре-рендерів і покращує продуктивність у складних формах.

2. **Як працює аутентифікація за JWT? Де зберігається токен?**
   Клієнт надсилає логін/пароль і отримує JWT, який складається з даних (payload) та підпису. У нашому проєкті токен зберігається в `localStorage` (через Zustand persist). Це просто в реалізації, але несе ризик XSS-атак (викрадення через шкідливі скрипти). Більш безпечна альтернатива — зберігання токенів у `httpOnly` cookies.

3. **Що таке Zod і які переваги він дає? Чим відрізняються z.input та z.output?**
   Zod — це бібліотека для опису схем даних. Її перевага — автоматична генерація TypeScript-типів на основі схеми. `z.input` — це тип даних, що надходить із форми (наприклад, рядок), а `z.output` — тип після трансформацій (наприклад, після конвертації рядка у число). `z.preprocess` потрібен, щоб перетворити порожній рядок (`''`), який приходить з input type="number", на `undefined`, інакше числова валідація видасть помилку.

4. **Поясніть концепцію захищених маршрутів.**
   Захищений маршрут (`ProtectedRoute`) — це компонент-обгортка, який перевіряє наявність токена або прав доступу. Якщо їх немає, він блокує рендер сторінки і виконує редирект (наприклад, через `<Navigate to="/login" />`). Однак клієнтський захист — це лише UI-зручність (код можна обійти в браузері); справжня безпека завжди забезпечується серверними мідлварами.

5. **Порівняйте Context API та Zustand. Чому серверні дані краще в TanStack Query?**
   Context API при оновленні значення перемальовує всіх споживачів, тоді як Zustand дозволяє підписуватися лише на конкретні частини стану (через селектори). Серверні дані краще зберігати в TanStack Query, бо він "з коробки" вирішує проблеми кешування, фонового оновлення даних, повторних запитів при помилках та інвалідації застарілого кешу.

6. **Що таке ключ запиту в TanStack Query? Що робить invalidateQueries?**
   Ключ запиту (наприклад, `['users', { page, search }]`) унікально ідентифікує запит у кеші. Якщо параметри змінюються, виконується новий запит. `invalidateQueries` позначає певний ключ (або групу ключів) як застарілий. Після цього TanStack Query автоматично робить новий запит до сервера, щоб оновити дані на екрані (наприклад, після видалення запису).

7. **Що таке оптимістичні оновлення?**
   Це патерн, коли інтерфейс оновлюється миттєво після дії користувача, не чекаючи відповіді від сервера (передбачаючи успіх). Якщо сервер повертає помилку, інтерфейс "відкочується" назад. Це доцільно для швидких некритичних дій (лайки, перемикачі), але не підходить для критичних операцій (оплата, видалення важливих даних).

8. **Як реалізувати централізовану обробку помилок?**
   1. Interceptors в Axios відловлюють помилки мережі глобально (наприклад, 401 для виходу). 
   2. Error Boundary ловить помилки JS у компонентах і замість "білого екрана" показує резервний UI. 
   3. Бібліотеки на кшталт `toast` дозволяють викликати красиві сповіщення про помилки з будь-якого місця коду єдиним форматом.

9. **Навіщо потрібен debounce для пошукового поля?**
   Debounce затримує виконання функції (наприклад, на 300 мс) після останнього натискання клавіші. Без нього під час введення слова "Іван" на сервер відправилося б 4 окремих запити (І, Ів, Іва, Іван), що створює зайве навантаження на БД та мережу.

10. **Що таке скелетні індикатори завантаження?**
    Це візуальні "заглушки" (сірі блоки, що блимають), які повторюють форму майбутнього контенту, поки він вантажиться. Вони покращують UX, оскільки запобігають різким стрибкам інтерфейсу (layout shift) і психологічно роблять очікування коротшим, ніж при використанні звичайного "спіннера".
